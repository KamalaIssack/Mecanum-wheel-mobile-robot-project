# Firmware State Report — `mecanum_drive` (Nucleo-F446RE)

Generated by full line-by-line read of every file in `Core/` and `mecanum_drive.ioc`. Files read in full: `mecanum_drive.ioc`, `Core/Inc/main.h`, `Core/Src/main.c`, `Core/Src/stm32f4xx_hal_msp.c`, `Core/Src/stm32f4xx_it.c`, `Core/Inc/stm32f4xx_it.h`. These are the **only** application source files in the project (`Core/Src/syscalls.c`, `sysmem.c`, `system_stm32f4xx.c` are the standard toolchain-generated files and contain no application logic; `Drivers/` is vendor HAL code, out of scope).

Per `mecanum_drive.ioc`, `Mcu.IPNb=5` — only **NVIC, RCC, SYS, TIM3, TIM4** are configured as IPs. No USART peripheral block, no other timer, no ADC/DMA/I2C/SPI is instantiated in CubeMX, despite pins being wired for USART2 (see §7).

## 1. Timers

Only **TIM3** and **TIM4** are configured. TIM1, TIM2, TIM5, TIM6, TIM7, TIM8 are **not configured at all** — no clock enable, no handle, nothing in `.ioc` or `main.c`.

Clock tree (from `.ioc` RCC section and `SystemClock_Config()` in `main.c`):
- Oscillator: **HSI** (16 MHz internal), NOT HSE, despite `RCC.HSE_VALUE=8000000` being present in the `.ioc` (see §7 note on unused HSE pins).
- PLL: `PLLM=8`, `PLLN=180`, `PLLP=DIV2`, source = HSI → VCO in = 16/8 = 2 MHz → VCO out = 2×180 = 360 MHz → SYSCLK = 360/2 = **180 MHz**.
- Over-Drive mode enabled (`HAL_PWREx_EnableOverDrive()`) — required to run the F446 at 180 MHz.
- AHB (HCLK) = 180 MHz (`RCC_SYSCLK_DIV1`)
- APB1 = HCLK/4 = 45 MHz, **APB1 timer clock = 90 MHz** (x2 multiplier applies because the APB1 prescaler ≠ 1)
- APB2 = HCLK/2 = 90 MHz, APB2 timer clock = 180 MHz (unused — no APB2 timers configured)

TIM3 and TIM4 are both APB1 timers on the F446, so both run off the **90 MHz APB1 timer clock**.

### TIM3
| Field | Value |
|---|---|
| Mode | PWM Generation, 4 channels (CH1–CH4), no encoder/IC |
| Clock source | Internal, APB1 timer clock = 90 MHz |
| Prescaler (PSC) | 89 |
| Counter Period (ARR) | 999 |
| Counter mode | Up |
| Clock division | DIV1 |
| Auto-reload preload | **Disabled** |
| Master output trigger | `TIM_TRGO_RESET` (no slave sync) |
| OC mode (all 4 ch) | PWM1, polarity HIGH, fast mode OFF, initial pulse = 0 |

**PWM frequency arithmetic:**
```
f_PWM = TIM_CLK / ((PSC+1) × (ARR+1))
      = 90,000,000 / ((89+1) × (999+1))
      = 90,000,000 / (90 × 1000)
      = 90,000,000 / 90,000
      = 1000 Hz  (1 kHz)
```
Duty resolution: 1000 steps (0–999), matching the firmware's `motor_set()` clamp of duty to 999.

### TIM4
Identical configuration to TIM3: PSC = 89, ARR = 999, same clock source (APB1, 90 MHz), same PWM1 mode on all 4 channels. **PWM frequency = 1000 Hz**, same arithmetic as above.

## 2. PWM Channels — Timer/GPIO/Motor Mapping

Each physical motor uses **two** PWM channels (RPWM/LPWM, direction via which channel carries duty — see §5 `motor_set()`), plus two GPIO enable lines (REN/LEN).

| Motor | Timer | RPWM Ch (fwd) | RPWM Pin | LPWM Ch (rev) | LPWM Pin | REN pin | LEN pin |
|---|---|---|---|---|---|---|---|
| **M1 (FL)** | TIM3 | CH1 | PA6 | CH2 | PA7 | PC0 | PC1 |
| **M2 (FR)** | TIM3 | CH3 | PB0 | CH4 | PB1 | PC2 | PC3 |
| **M3 (RL)** | TIM4 | CH1 | PB6 | CH2 | PB7 | PC8 | PC9 |
| **M4 (RR)** | TIM4 | CH3 | PB8 | CH4 | PB9 | PC10 | PC11 |

Confirmed against `mecanum_drive()` in `main.c` (lines 402–413):
```c
motor_set(&htim3, TIM_CHANNEL_1, TIM_CHANNEL_2, GPIOC, M1_REN_Pin, M1_LEN_Pin, fl);
motor_set(&htim3, TIM_CHANNEL_3, TIM_CHANNEL_4, GPIOC, M2_REN_Pin, M2_LEN_Pin, fr);
motor_set(&htim4, TIM_CHANNEL_1, TIM_CHANNEL_2, GPIOC, M3_REN_Pin, M3_LEN_Pin, rl);
motor_set(&htim4, TIM_CHANNEL_3, TIM_CHANNEL_4, GPIOC, M4_REN_Pin, M4_LEN_Pin, rr);
```
This maps to a BTS7960/IBT-2-style dual-PWM-plus-enable driver: REN/LEN are enable lines held statically HIGH at startup (never toggled again), while RPWM/LPWM channels carry the actual PWM duty for direction+speed.

All 8 PWM outputs are started in `main()` before the loop:
```c
HAL_TIM_PWM_Start(&htim3, TIM_CHANNEL_1..4);
HAL_TIM_PWM_Start(&htim4, TIM_CHANNEL_1..4);
```

## 4. USART2 Configuration

**There is no USART2 configuration.** Explicitly verified:
- `mecanum_drive.ioc` `Mcu.IPNb=5` lists only `NVIC, RCC, SYS, TIM3, TIM4` — **USART2 is not an instantiated IP** in CubeMX.
- `main.c` has no `huart2` handle, no `MX_USART2_UART_Init()` function, no `#include` of USART-related init, and no `HAL_UART_Transmit`/`Receive` calls anywhere.
- `stm32f4xx_hal_msp.c` has no `HAL_UART_MspInit()` and, critically, **no `__HAL_RCC_USART2_CLK_ENABLE()`** anywhere — the peripheral clock is never turned on.
- `stm32f4xx_it.c` has no `USART2_IRQHandler`.

What *is* configured: PA2/PA3 are set to `GPIO_MODE_AF_PP`, `GPIO_AF7_USART2`, no pull, very-high speed, in `MX_GPIO_Init()` (lines 357–363 of `main.c`), and the `.ioc` labels them `USART_TX`/`USART_RX`. This wires the pins to the USART2 alternate function at the GPIO level only — the peripheral itself is dead (no clock, no baud rate, no word length, no parity, no interrupts, no DMA configured anywhere). **Baud rate: not configured. Word length: not configured. Interrupts/DMA: not configured — the peripheral doesn't exist yet.**

## 5. `main()` and Interrupt Handler Behavior

### `main()` (`Core/Src/main.c`)
1. `HAL_Init()` — resets peripherals, configures Flash prefetch/Systick.
2. `SystemClock_Config()` — HSI → PLL → 180 MHz SYSCLK with Over-Drive, APB1=45 MHz, APB2=90 MHz, as detailed in §1.
3. `MX_GPIO_Init()` — enables GPIOA/B/C/H clocks; drives all 8 motor enable pins (M1–M4 REN/LEN) and LD2 LOW; configures B1 as falling-edge interrupt input; configures the 8 motor enable pins as push-pull outputs; configures PA2/PA3 as USART2 AF pins (pins only, no peripheral); configures LD2 as push-pull output.
4. `MX_TIM3_Init()` — configures TIM3 PWM (PSC=89, ARR=999) on all 4 channels, PWM1 mode, then calls `HAL_TIM_MspPostInit(&htim3)` which sets PA6/PA7/PB0/PB1 to AF2 (TIM3).
5. `MX_TIM4_Init()` — identical for TIM4, `HAL_TIM_MspPostInit(&htim4)` sets PB6–PB9 to AF2 (TIM4).
6. **USER CODE 2**: starts all 8 PWM channels via `HAL_TIM_PWM_Start()`, then drives all 8 motor-driver enable pins (M1–M4 REN/LEN) HIGH — permanently enabling all four motor drivers.
7. **Infinite `while(1)` loop** — a hardcoded, open-loop test sequence with no sensor input, no serial command parsing, and no feedback of any kind:
   ```c
   mecanum_drive(500, 0, 0);   // drive forward at 50% speed
   HAL_Delay(2000);
   mecanum_drive(0, 0, 0);     // stop
   HAL_Delay(1000);
   mecanum_drive(0, 500, 0);   // strafe right at 50% speed
   HAL_Delay(2000);
   mecanum_drive(0, 0, 0);     // stop
   HAL_Delay(1000);
   // loop repeats forever
   ```
   The source comments explicitly label these as `/* Test: ... */` — this is a demo/bring-up routine, not a real control loop.

### Helper functions (USER CODE 4, `main.c`)

**`motor_set(htim, rpwm_ch, lpwm_ch, en_port, ren_pin, len_pin, speed)`**
- `duty = |speed|`, clamped to 999 (matches ARR).
- `speed > 0`: RPWM channel CCR = duty, LPWM channel CCR = 0 (forward).
- `speed < 0`: RPWM channel CCR = 0, LPWM channel CCR = duty (reverse).
- `speed == 0`: both channels CCR = 0 (coast/stop). REN/LEN enable pins are **not** touched here — they were set HIGH once in `main()` and stay HIGH permanently, so `motor_set(..., 0)` produces electrical braking/coast depending on the driver IC, not a disabled driver.

**`mecanum_drive(vx, vy, omega)`** — standard mecanum inverse kinematics:
```c
fl = vx - vy - omega;
fr = vx + vy + omega;
rl = vx + vy - omega;
rr = vx - vy + omega;
```
then calls `motor_set()` once per wheel as shown in §2.

### Interrupt handlers (`stm32f4xx_it.c`)
Only the **Cortex-M core exception handlers** are present, all in their default CubeMX-generated form:
- `NMI_Handler` — infinite `while(1)` trap.
- `HardFault_Handler`, `MemManage_Handler`, `BusFault_Handler`, `UsageFault_Handler` — each an infinite `while(1)` trap (no fault diagnostics).
- `SVC_Handler`, `DebugMon_Handler`, `PendSV_Handler` — empty bodies (default RTOS-less stubs).
- `SysTick_Handler` — calls `HAL_IncTick()` only.

**No peripheral interrupt handlers exist at all** — no `TIM3_IRQHandler`, `TIM4_IRQHandler`, `EXTI15_10_IRQHandler`, or `USART2_IRQHandler`. This is consistent with the peripherals being used in polling/non-interrupt mode (`HAL_TIM_PWM_Start`, not `_IT` or `_DMA` variants) — except for the B1 button, which *is* configured for a hardware interrupt but has no path to an ISR (see §7).

## 6. Encoder / Input Capture

**None exists.** Confirmed by:
- `.ioc` `Mcu.IPNb=5` — only NVIC, RCC, SYS, TIM3, TIM4 are instantiated; no `TIM.Channel-Input Capture` or `TIM.Encoder` keys appear anywhere in the file.
- TIM3 and TIM4 are both configured purely for `PWM Generation` on all 4 channels each (`SH.S_TIM3_CH1.0=TIM3_CH1,PWM Generation1 CH1`, etc.) — no channel is set to Input Capture or Encoder mode.
- No other timer (TIM1/2/5/6/7/8) is configured at all, so there's no timer left over for encoder use.
- No GPIO pin in `main.h` or the `.ioc` is labeled or purposed as an encoder input.

If wheel odometry is planned, it is entirely unimplemented — no hardware resource is currently reserved for it.

## 7. TODOs, Half-Finished Code, and Inconsistencies

1. **USART2 pins wired but peripheral dead.** PA2/PA3 are configured at the GPIO level for USART2 AF7 and labeled `USART_TX`/`USART_RX` in the `.ioc`, but USART2 is not in the CubeMX IP list, has no HAL handle, no clock enable (`__HAL_RCC_USART2_CLK_ENABLE()` is absent), no baud/init, and no IRQ handler. Any code path that assumes serial control input exists would not work — the peripheral has never been brought up.

2. **Blue pushbutton (PC13/B1) interrupt is armed but unreachable.** GPIO is configured `GPIO_MODE_IT_FALLING` (EXTI13 armed at the GPIO/EXTI level), but:
   - NVIC does not enable `EXTI15_10_IRQn` anywhere (not in the `.ioc` NVIC list, no `HAL_NVIC_EnableIRQ()` call in code).
   - No `EXTI15_10_IRQHandler` exists in `stm32f4xx_it.c`.
   - No `HAL_GPIO_EXTI_Callback()` / `HAL_GPIO_EXTI_Falling_Callback()` is implemented anywhere.
   Net effect: pressing the button currently does nothing — the interrupt line is set but masked at the NVIC and has no handler even if unmasked.

3. **`main()`'s control loop is a fixed demo sequence, not a real drive loop.** It is explicitly commented `/* Test: ... */` and hardcodes forward/strafe motion with `HAL_Delay()`, with no input source (no serial, no encoder, no button, no timer-based scheduling). This looks like bring-up/test code left in place rather than the intended final application loop.

4. **TIM1, TIM2, TIM5, TIM6, TIM7, TIM8 are entirely unused** — no clock, no handle, no `.ioc` entry. If additional PWM channels, input capture, or a time-base for a control loop are needed later, none of these are currently reserved.

5. **LD2 (PA5, green LED) is configured but never used** in application logic — set low at init and never written again. No heartbeat/status indication despite being available.

6. **Auto-reload preload is disabled on both TIM3 and TIM4**, and `HAL_TIM_PWM_ConfigChannel()` does not explicitly enable capture/compare preload either. Since `ARR` is never changed at runtime this has no practical effect, but only `CCR` (duty) is updated on the fly via `__HAL_TIM_SET_COMPARE()` inside `motor_set()` — worth confirming preload behavior explicitly if duty updates are ever moved to occur mid-cycle at high update rates.

7. **Motor enable lines (REN/LEN) are set HIGH once at startup and never touched again.** `motor_set(..., 0)` (stop) only zeroes both PWM duty cycles — it does not deassert REN/LEN. Depending on the specific motor driver IC in use, this means "stop" is electrical coast/brake via 0% duty rather than a driver-disable, which may or may not be the intended safety behavior.

8. **HSE oscillator pins (PH0/PH1) are reserved in the pinout but HSE is not the selected clock source** — `SystemClock_Config()` uses `RCC_OSCILLATORTYPE_HSI` with `RCC_PLLSOURCE_HSI`, while the `.ioc` RCC block still carries `RCC.HSE_VALUE=8000000`. This is not a functional bug (HSI is explicitly and correctly used), but is a leftover/inconsistent artifact from the default board template — no HSE crystal is actually driving the clock.

9. File headers throughout the project use `Copyright (c) 2026 STMicroelectronics` — this is STM32CubeIDE's template boilerplate reflecting the generation date, not a functional issue.
